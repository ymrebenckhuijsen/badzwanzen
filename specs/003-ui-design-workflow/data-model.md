# Phase 1 Data Model: UI-design-stap in de spec-driven workflow

This feature has no application data model (no runtime entities, no persistence layer beyond
files the workflow itself reads/writes). The "entities" below are files and Stitch resources
that the `speckit-design` skill reads from and writes to.

## Root `DESIGN.md` (repository root)

The canonical, project-wide design system document. One instance, shared across all features.

| Field | Description |
|---|---|
| Design system reference | Stitch design system asset id backing this doc (project `2820714669126137113`, "Party Quest") |
| Color tokens | Primary/secondary/tertiary + game-state colors, dark-mode values |
| Typography tokens | Font families (Rubik, Be Vietnam Pro) and scale |
| Component style | Shape/spacing conventions (e.g. pill-shaped buttons) |
| Screens index | List of Stitch screens contributed by each feature, with links back to that feature's addendum |
| Last updated by | Feature branch name of the most recent update |
| Tailwind mapping | Pointer to `design/tailwind-theme.css`, a generated Tailwind v4 `@theme` mirror of these same tokens (see below) |

**Lifecycle**: Created once (bootstrap, by this feature — see research.md), then updated
in-place by every subsequent UI-affecting feature's `speckit-design` run. Never per-feature —
there is exactly one.

## `design/tailwind-theme.css` (repository root)

A generated Tailwind v4 `@theme` mirror of the root `DESIGN.md`'s tokens (colors, fonts, font
sizes, radii, spacing) — see `contracts/design-addendum-format.md` for the exact token→CSS-key
mapping. Not hand-authored; regenerated by `speckit-design` in lockstep with root `DESIGN.md`,
same lifecycle and idempotency rule (no-op write if tokens didn't change). Exists so an
implementer can use Tailwind utility classes (`bg-primary`, `font-display`, `rounded-xl`, …)
directly instead of re-deriving them from prose (FR-010).

## Feature addendum `DESIGN.md` (`specs/[###-feature]/DESIGN.md`)

One instance per feature. Created the first time `speckit-design` runs for that feature
(whether triggered from `before_plan` or `before_tasks`).

| Field | Description |
|---|---|
| `Status` (frontmatter) | One of: `Draft`, `Changes Requested`, `Approved`, `No UI Impact` — see Design Review Status below |
| Root reference | Link to the repository-root `DESIGN.md` this addendum extends |
| Screens | Stitch screen resource names (`projects/{project}/screens/{screen}`) this feature added or edited, each paired with a **committed screenshot** at `specs/[feature]/design/<screen-slug>.png` (the actual reviewed artifact) plus the Stitch project link (secondary, for interactive editing) |
| What this feature adds/changes | Short prose description of new screens or deviations from the shared design system |
| Review history | Append-only short log of change-request rounds (what was asked, what changed) — not a separate entity, just prose in this same file |

**Lifecycle**: `Draft` (just generated) → `Changes Requested` (zero or more rounds, looping
back to a new Stitch generation/edit) → `Approved` (developer explicit approval; unlocks
`/speckit-tasks`/`/speckit-implement`). Or, for a feature with no UI impact: created directly
in the `No UI Impact` state on first run, which is terminal — this state exists specifically so
a later `before_tasks` firing doesn't re-ask the "does this have UI impact" question (FR-007,
SC-004).

## Design Review Status (state machine, lives in the addendum's `Status` field)

```text
(no addendum file yet)
        |
        v  developer confirms UI impact
     Draft ------------------------------> Approved
        |            developer approves        ^
        | developer requests changes           |
        v                                       |
Changes Requested  -----> (regenerate/edit) -----+
        ^                        |
        +------------------------+
              further change requests

(no addendum file yet)
        |
        v  developer confirms NO UI impact
   No UI Impact   (terminal — before_plan and before_tasks both short-circuit immediately)
```

`/speckit-tasks` and `/speckit-implement` (FR-006) are blocked by the `before_tasks` hook
unless `Status` is `Approved` or `No UI Impact`.

## Stitch design system (external resource, not a repo file)

Referenced, not owned, by this feature. Lives in Stitch as project `2820714669126137113`
("Party Quest"), fetched via `mcp__stitch__list_design_systems` / `get_project`. Its tokens are
mirrored (not duplicated as a separate source of truth) into the root `DESIGN.md`.

## Stitch screen (external resource, not a repo file)

One Stitch screen per feature-specific UI concept, created via `generate_screen_from_text` or
modified via `edit_screens`. Referenced from the feature addendum by resource name
(`projects/{project}/screens/{screen}`); the addendum is what ties a Stitch screen back to the
feature and requirement that produced it.
